# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is `~/.config` on an Arch Linux (Hyprland/Wayland) desktop, tracked with git. There is no build system, no tests, and no application source code — every file here is a live configuration file consumed directly by the corresponding program. Editing a file in this repo changes the user's running desktop environment (after a reload/restart of the relevant program).

There is no README and no existing CLAUDE.md prior to this one.

## Repo scope and .gitignore

Only a subset of `~/.config` is tracked. [.gitignore](.gitignore) excludes machine-local, cache, or secret-bearing directories: `Code/`, `dconf/`, `glib-*/`, `gtk-*/`, `matplotlib/`, `pulse/`, `qalculate/`, `OpenRGB/`, `vlc/`, `warp-terminal/`, `xfce4/`, `inkscape/`, `qt5ct/`, `user-dirs.*`, `QtProject.conf`, `mimeapps.list`, `Kitware/CMakeSetup.conf`, `GIMP/`, `remmina/`, `freerdp/`, plus `secrets/` (credentials), `zsh/.zsh_history`, `zsh/.zcompdump*`, and `wallust/current` (all per-machine state).

Generated colour files, by contrast, ARE tracked — see the GTK note in the theming section for why (a fresh clone would otherwise have a broken compositor config).

**Every pattern in .gitignore is anchored with a leading `/`.** This matters: an unanchored pattern like `gtk-*/` matches at *any* depth, so it silently excluded `themes/Sweet-Custom/gtk-{2,3,4}.0/` — the actual GTK theme — while still tracking that theme's 3369-file `node_modules`. Keep new patterns anchored to the repo root.

`systemd/` uses a selective ignore: generated `*.target.wants/` state is excluded, but the hand-authored `systemd/user/*.service`, `*.target`, and `*.service.d/*.conf` files ARE tracked via `!` negation rules. Don't assume a path's tracked state from a top-level directory name — run `git check-ignore -v <path>` when in doubt, since ignore rules and tracked state can diverge over time. When adding new config directories, check whether they contain machine-specific state (caches, history, tokens, hardware IDs) before `git add`-ing them; prefer ignoring those and committing only the human-authored settings files. The vendored theme's npm build tree (`themes/Sweet-Custom/node_modules/`, `package-lock.json`, `*.css.map`) is ignored — it's reproducible from `package.json` — while the compiled theme (`gtk-*`, `assets/`, `index.theme`) is tracked.

## Architecture: how the pieces fit together

This is a Hyprland (wlroots Wayland compositor) desktop. The pieces are wired together through [hypr/hyprland.lua](hypr/hyprland.lua), which is the entry point for the whole session.

**The compositor config is Lua, not hyprlang.** hyprlang was deprecated in Hyprland 0.55 and the 0.56.1 binary warns that `.conf` support is *removed in 0.57* (`strings /usr/bin/Hyprland | grep 'removed in Hyprland'`). `hyprland.lua` is split into modules that `hyprland.lua` `require`s — each gets its own Lua scope, so a syntax error in one does not take down the whole config:

| file | contents |
|---|---|
| [hypr/hyprland.lua](hypr/hyprland.lua) | entry point; nothing but `require` calls |
| [hypr/monitors.lua](hypr/monitors.lua) | `hl.monitor` + the odd/even workspace→monitor rules |
| [hypr/programs.lua](hypr/programs.lua) | returns a table of program names (replaces the old `$vars`) |
| [hypr/env.lua](hypr/env.lua) | `hl.env(...)` |
| [hypr/looknfeel.lua](hypr/looknfeel.lua) | `hl.config{general,decoration,...}`, curves, animations |
| [hypr/autostart.lua](hypr/autostart.lua) | `hl.on("hyprland.start", ...)` (replaces `exec-once`) |
| [hypr/binds.lua](hypr/binds.lua) | `hl.bind(...)` |
| [hypr/rules.lua](hypr/rules.lua) | `hl.window_rule(...)` |
| `hypr/theme/colors.lua` | **GENERATED** by wallust; `require`d by looknfeel.lua |

`hyprland.conf` is intentionally still present as a **zero-cost rollback**: Hyprland loads `hyprland.lua` only if it exists, else the `.conf`. To revert, `mv hypr/hyprland.lua hypr/hyprland.lua.off && hyprctl reload full-reset`. It is otherwise dead — do not edit it, and do not expect changes there to take effect.

Reference material ships with the package and is far more reliable than the wiki for exact field names: `/usr/share/hypr/hyprland.lua` (upstream example) and `/usr/share/hypr/stubs/hl.meta.lua` (a 1770-line typed stub listing every option, dispatcher and spec field). Note the stub is autogenerated and *lags* in places — it omits `mouse` from `HL.BindOptions` even though the shipped example uses `{ mouse = true }` for `bindm`-style binds. When they disagree, prefer the example and verify with `hyprctl configerrors`.

Only the *compositor* moved to Lua. `hyprlock.conf`, `hypridle.conf` and `hyprpaper.conf` belong to separate Hypr\* projects and are still hyprlang.

- **Session startup**: greetd launches the session through **uwsm** (Universal Wayland Session Manager) — `uwsm start -e -D Hyprland hyprland.desktop`, set in the out-of-repo `/etc/greetd/config.toml` (see the outside-this-repo section). uwsm runs the compositor inside `wayland-wm@hyprland.desktop.service`, sets up the systemd/D-Bus user environment deterministically, owns `graphical-session{,-pre}.target`, and tears the session down cleanly on logout. This replaced a bare `start-hyprland` launch whose racy environment intermittently left `waybar` and keybind-launched apps broken on login (especially logout→login within one boot). Autostart lives in [hypr/autostart.lua](hypr/autostart.lua) as a single `hl.on("hyprland.start", ...)` callback (Lua's replacement for `exec-once`); commands run in the order written. **This event does NOT fire on `hyprctl reload`**, which is convenient (a reload cannot duplicate your daemons) but means autostart changes are only exercised by a real logout/login. To test the mechanism without logging out, run a nested Hyprland against a throwaway config: `SENTINEL=/tmp/s XDG_CONFIG_HOME=/tmp/nested timeout 25 Hyprland` with a one-line `hl.on("hyprland.start", ...)` that touches the sentinel. The one **mandatory** entry is `uwsm finalize HYPRLAND_INSTANCE_SIGNATURE`, which exports the compositor's runtime vars into the systemd/D-Bus env and completes the compositor unit — omit it and the session start times out. The rest launch a terminal, a guarded `HDMI-A-1` re-enable fallback (see the multi-monitor note in the outside-this-repo section), clipboard tooling (`wl-paste`/`cliphist`/`wl-clip-persist`), `xwaylandvideobridge`, `waybar`, and the wallpaper via `wallust/set-wallpaper` (awww — hyprpaper is no longer used, see the theming section). The graphical-session daemons — `hypridle` (idle/lock, [hypr/hypridle.conf](hypr/hypridle.conf)), `hyprsunset` (blue-light filter), `swaync` (notifications), and `hyprpolkitagent` (polkit agent) — are NOT started from `autostart.lua`; they are `enable`d systemd user units that uwsm pulls in via `graphical-session.target`, with the correct environment, after `finalize`. **Don't also add an autostart entry for a daemon that has an enabled unit, or it will run twice** — this bit both `hypridle` and `swaync`. `swaync` is the subtler case: it ships D-Bus service files with `SystemdService=swaync.service`, so the first notification request activates the unit even when the unit is `disabled`, and an autostart copy holding the D-Bus name makes it fail with "An instance of SwayNotificationCenter is already running!" until it hits its restart limit. If a daemon owns a well-known D-Bus name, let systemd start it.
- **Program names** live in [hypr/programs.lua](hypr/programs.lua), which returns a table (`prog.terminal`, `prog.menu`, `prog.shot`, …) that `binds.lua` and `autostart.lua` `require`. This replaced the old `$terminal`-style hyprlang variables. Change the table entry, not each `hl.bind` line, when swapping an app.
- **hyprlock** ([hypr/hyprlock.conf](hypr/hyprlock.conf)) is the lock screen, invoked via `pidof hyprlock || hyprlock` (idempotent — never launches a second instance). It `source`s the generated `hypr/theme/colors.conf` for its palette. hyprlock has **no config-validation flag**; to parse-test it without locking your session, point it at a nonexistent display: `WAYLAND_DISPLAY=x hyprlock -v --display x 2>&1 | grep 'does not exist'` (the config is read before the connection attempt).
- **Waybar** ([waybar/config.jsonc](waybar/config.jsonc), [waybar/style.css](waybar/style.css)) is the status bar. `style.css` contains **zero color literals** — it `@import`s the generated `waybar/colors.css` and derives every translucent shade with GTK CSS's `alpha(@name, 0.24)`. Beyond the custom modules below it runs `idle_inhibitor` (suppresses the hypridle 300s lock — useful for video) and `mpris` (now-playing, in the otherwise-empty center). There is deliberately **no `bluetooth` module**: bluez is not installed and the machine has no radio. Custom modules shell out to scripts in the same directory:
  - `custom/night-mode` → [waybar/night-mode.sh](waybar/night-mode.sh) (renders icon/tooltip/class) and [waybar/night-mode-toggle.sh](waybar/night-mode-toggle.sh) (flips it, called both from Waybar's `on-click` and from the `SUPER+N` keybind). Both scripts talk to `hyprsunset` over its IPC (`hyprctl hyprsunset temperature`), which is the single source of truth — there is no state file, so the two entry points cannot disagree. The toggle retunes the running daemon in place (day 6000K / night 3400K) and signals Waybar (`SIGRTMIN+10`, wired via the module's `"signal": 10`) to refresh immediately. `hyprsunset` itself runs as a systemd unit, so the toggle must never `pkill`/re-spawn it.
  - `custom/gpu` → [waybar/gpuinfo.sh](waybar/gpuinfo.sh); `custom/power` → [waybar/power-menu.sh](waybar/power-menu.sh).
- **rofi** ([rofi/config.rasi](rofi/config.rasi)) is the app launcher (`prog.menu`), the clipboard picker (`cliphist list | rofi -dmenu | cliphist decode | wl-copy`, `SUPER+V`), the power menu, and the theme picker. It `@import`s the generated `rofi/colors.rasi`. Its `icon-theme` is `Sweet-Purple`, matching GTK and Qt.
- **swaync** ([swaync/config.json](swaync/config.json), [swaync/style.css](swaync/style.css)) is the notification daemon. `style.css` `@import`s the generated `swaync/colors.css` and uses `@define-color`/`alpha()`; it previously used `:root { --var }` + `var()`, which are web-CSS custom properties GTK only supports in recent GTK4 — prefer `@define-color` in any GTK stylesheet here.
- **superfile** ([superfile/config.toml](superfile/config.toml), [superfile/hotkeys.toml](superfile/hotkeys.toml), `superfile/theme/*.toml`) is a TUI file manager (`spf`), launched via `prog.file_manager = alacritty -e spf`. `config.toml`'s `theme` key selects `wallust`, which is generated; the other files in `theme/` are vendored upstream options and inert.
- **Alacritty** ([alacritty/alacritty.toml](alacritty/alacritty.toml)) is the canonical system terminal: it is `prog.alt_terminal`, backs `prog.file_manager`, is what Nemo's "Open in Terminal" launches, and is the target of Waybar click-actions. `prog.terminal` (`warp-terminal`, `SUPER+Q`) is the interactive daily driver but is deliberately not wired into system integration points. Colours come from `[general] import = ["~/.config/alacritty/colors.toml"]` — the importing file is loaded **last**, so never put colour settings in `alacritty.toml` itself or they will override the generated palette. When changing the system terminal, update both `programs.lua` and the Nemo gsetting below. (`alacritty.yml` was deleted — Alacritty dropped YAML in 0.13, so it had been inert while carrying 30 duplicate colours.)
- **Nemo** is `prog.gui_file_manager` (`SUPER+B`). Two integration points live *outside* this repo, in untracked state, so they aren't obvious from the tracked files: its "Open in Terminal" target is `org.cinnamon.desktop.default-applications.terminal` `exec`/`exec-arg` in dconf (set to `alacritty -e`), and archive Compress/Extract requires the `nemo-fileroller` extension plus `file-roller` registered as the default handler for archive MIME types in the (gitignored) `mimeapps.list`. If those regress, check `gsettings get ...terminal exec` and `xdg-mime query default application/zip`, not a config file here.

## Things that live outside this repo

Several fixes for this desktop can't be stored here, because they're system paths. Most are self-documenting (read the file's header comment), but they won't show up in `git log`:

- **The greeter is ReGreet** (GTK4), run inside a `cage` kiosk compositor: `/etc/greetd/config.toml` → `dbus-run-session cage -s -mlast -- regreet`. It replaced tuigreet (backup: `config.toml.bak-tuigreet`). Config is `/etc/greetd/regreet.toml`; `/etc/greetd/regreet.css` is **generated** by wallust and installed with `doas` by `theme-switch`, so the login screen follows the desktop palette.

  Three non-obvious constraints, all learned the hard way:
  - **The greeter runs as uid 968 (`greeter`) and cannot read `/home/edargham`** (mode `drwx--x---`). So the GTK theme is installed system-wide at `/usr/share/themes/Sweet-Custom` (an rsync of the repo copy, minus SCSS/node_modules) and the wallpaper is copied to `/usr/share/backgrounds/greeter.jpg`. Pointing `regreet.toml` at anything under `$HOME` silently falls back to Adwaita / no background. Test access with `doas setpriv --reuid=968 --regid=968 --clear-groups test -r <path>` — **never** `doas -u greeter`, which tries to *authenticate* and will rack up faillock tallies against your own account.
  - **Unlike tuigreet, the session command is not in `config.toml`.** tuigreet took `-c 'uwsm start …'`; ReGreet launches whichever entry is picked from `/usr/share/wayland-sessions`. `hyprland.desktop` runs bare `/usr/bin/start-hyprland` — the racy path this desktop deliberately migrated away from — so it is masked with `NoDisplay=true`, re-applied after hyprland upgrades by `/etc/pacman.d/hooks/95-mask-bare-hyprland-session.hook`. Only `hyprland-uwsm.desktop` is selectable.
  - `regreet --demo` runs the full UI without a greetd socket, so it can be smoke-tested live: `cage -s -- regreet --demo --verbose`, then `grim` the result. Use this before ever restarting greetd. `/var/log/regreet` and `/var/lib/regreet` must exist and be owned by `greeter`.

  **Recovery if the greeter fails:** switch to a TTY (ctrl-alt-F2 — `cage -s` is what keeps VT switching possible) and run `doas cp /etc/greetd/config.toml.bak-tuigreet /etc/greetd/config.toml && doas systemctl restart greetd`.

- **Multi-monitor boot/greeter + session launch** (all outside this repo). The secondary monitor `HDMI-A-1` is force-disabled at boot via `video=HDMI-A-1:d` in the systemd-boot entry `/boot/loader/entries/arch.conf`, so the Plymouth splash and the greeter render on the primary (`DP-1`) only. On this NVIDIA GPU that kernel force reports the connector `disconnected` for the *whole* session and only applies at boot, so a `pam_exec` hook in `/etc/pam.d/greetd` runs `/usr/local/bin/reenable-hdmi` (self-documenting header) to force the connector **off whenever the greeter shows** and **re-probe it on** (`echo detect > /sys/class/drm/*-HDMI-A-1/status`) for the real user's desktop. The entry in `autostart.lua` is only a guarded fallback for that re-probe. greetd's session command in `/etc/greetd/config.toml` launches Hyprland via `uwsm start` (backup: `config.toml.bak-uwsm`; PAM hook backup: `greetd.bak-multimon`). If HDMI-A-1 is ever missing on the desktop, `doas /bin/sh -c 'echo detect > /sys/class/drm/card1-HDMI-A-1/status'` recovers it.

- **`/usr/local/bin/file-roller`** — a wrapper that runs file-roller under `GDK_BACKEND=x11`. file-roller 44.7 (the newest in [extra]; the AUR package is *older*) segfaults on window teardown under the GTK4 **Wayland** backend — it fails a `gdk_surface_get_display` assertion and dies in `gtk_window_destroy`, dumping core on every Compress/Extract. The archive is written correctly first, so it's cosmetic, but it's noisy. Measured 3/3 crashes on Wayland vs 0/3 on x11; reproduces with the stock Adwaita theme, so it is *not* caused by Sweet-Custom or any local setting. Both entry points resolve the bare name `file-roller` through `PATH` (nemo-fileroller spawns the binary; `org.gnome.FileRoller.desktop` uses `Exec=file-roller %U`), and `/usr/local/bin` precedes `/usr/bin`, so one shim covers both. Re-test with `GDK_BACKEND=wayland file-roller --add-to=/tmp/t.zip /etc/hostname` after any gtk4/file-roller update and delete the wrapper once it stops crashing.
- **`/etc/ld.so.conf.d/torch.conf`** — puts `/usr/local/libtorch/lib` on the **global** library search path, which makes libtorch's bundled `libnl-3.so.200` shadow the system `libnl` (3.12.0) for *every process on the machine*, not just torch ones. `ldconfig -p | grep libnl-3.so.200` shows both, libtorch first. The visible symptom is `waybar: /usr/local/libtorch/lib/libnl-3.so.200: no version information available` on every waybar start; anything else using libnl (networking tools, waybar's network module) is equally exposed. **Left as-is deliberately** — narrowing it to an `LD_LIBRARY_PATH` for torch processes only, or rebuilding with rpath, risks breaking the ML toolchain. Filter the warning rather than "fixing" it blindly, and don't mistake it for a waybar bug.
- **`/etc/systemd/coredump.conf.d/50-maxuse.conf`** — caps coredump storage at 1G. The default is 10% of `/var` (~45G here). Coredumps stay **enabled** deliberately: the file-roller bug above produced no failed unit and no journal error, and was only diagnosable because its core was retained.
- **systemd user units** back the long-running per-user daemons of the graphical session: [systemd/user/hyprsunset.service](systemd/user/hyprsunset.service) (blue-light filter), plus the package-provided `hypridle.service`, `swaync.service`, and `hyprpolkitagent.service` (all `enable`d and pulled in by `graphical-session.target`, which is now owned by **uwsm** — there is no hand-rolled session target anymore). [systemd/user/hyprpolkitagent.service.d/override.conf](systemd/user/hyprpolkitagent.service.d/override.conf) tweaks the polkit agent; note its unit carries `ConditionEnvironment=WAYLAND_DISPLAY`, so it must start *after* uwsm's `finalize` has exported the env — enabling it and letting uwsm pull it in satisfies that, whereas the old exec-once `systemctl --user start hyprpolkitagent` raced the env and crash-looped. A unit that is `WantedBy=`/`PartOf=` a target must not also `Requires=` it (systemd.special(7)) — that inverts the dependency; use `PartOf` + `After`.
- **themes/Sweet-Custom** is a large vendored GTK/Cinnamon theme (its own `package.json`/`Gulpfile.js`/SCSS build is upstream scaffolding, not something this repo builds — `node_modules` is untracked). GTK resolves it via `~/.themes/Sweet-Custom` and `~/.local/share/themes/Sweet-Custom`, which are **symlinks into `~/.config/themes/Sweet-Custom`** (GTK does not search `~/.config/themes`); leave those symlinks in place. **Theming is driven by standards, not env overrides** — see the next section. When editing theme colors, note the cyberpunk customization lives in the SCSS sources (`gtk-3.0/_colors.scss`, `widgets/*.scss`) AND is baked into the committed compiled CSS (`gtk-3.0/gtk.css`, `gtk-dark.css`); a hand edit to one without the other will drift, and a full SCSS rebuild would overwrite manual CSS edits.

## Theming: one palette, generated everywhere (wallust)

**The palette has exactly one source of truth.** It used to be re-typed as a literal in every consumer (~250 hardcoded values; `waybar/style.css` alone had 175 with no variables). Now [wallust](wallust/wallust.toml) renders ~22 templates from a single colorscheme.

```
wallust/wallust.toml            declares every template -> target
wallust/colorschemes/*.json     curated palettes, EXACT colours (pywal JSON format)
wallust/templates/              one template per consumer (+ templates/icons/*.svg)
wallust/theme-switch            the switcher (rofi picker; SUPER+SHIFT+T)
wallust/set-wallpaper           awww wallpaper setter, called by theme-switch + autostart
wallust/current                 active theme name (gitignored state)
```

Two theme sources, both handled by `theme-switch`:
- **Curated** — a file in `colorschemes/`, applied with `wallust cs <name>`. Colours are preserved *exactly*. `cyberpunk` is the house palette.
- **Built-in** — wallust ships ~617 named themes (`wallust theme list`), applied with `wallust theme <name>`. They render the same templates, so they work for free.

`theme-switch <name>` / `--list` / `--current`, or no argument for the picker. It regenerates everything then reloads in place: `hyprctl reload`, `pkill -USR2 waybar`, `swaync-client -rs`, a gsettings flip to make GTK re-read its user CSS, and the wallpaper last. rofi, hyprlock, superfile and Qt apps read colours at launch and so are not reloaded; alacritty watches its imported `colors.toml` itself.

**matugen was evaluated first and rejected** — do not reach for it here. It harmonizes `custom_colors` into a Material You scheme and cannot echo an exact palette (measured on 4.1.0: `#5de5ff`→`#83d2e4`, `#161925`→`#b6c4ff`). `blend = false` had no effect and `custom_keywords` has no working reference syntax.

### Writing wallust templates

wallust exposes only `color0`-`color15` + `background`/`foreground`/`cursor` — there are **no semantic names**, so the 16-slot mapping documented at the top of `wallust.toml` is the contract every template depends on. Read it before editing one.

Available filters (discovered empirically; the docs are thin): `lower`, `upper`, `strip` (drops `#`), `rgb` (→ `93,229,255`), `red`/`green`/`blue`, `complementary`. **Not** available: `rgba`, `xrgba`, `hex`, `alpha`, `to_upper`, and any lighten/darken/mix. Compose what you need in the template instead:

| need | template |
|---|---|
| CSS hex | `{{color2 \| lower}}` → `#5de5ff` |
| Hyprland | `rgba({{color2 \| strip \| lower}}aa)` |
| decimal rgba | `rgba({{color2 \| rgb}}, 0.24)` |
| Qt ARGB | `#ff{{color2 \| strip \| lower}}` |

Literal `{` is fine (CSS templates work); only `{{` is special, so an empty `{{ }}` in a comment is a syntax error. Because there are no shade filters, derived shades must come from the *consumer*: GTK templates use CSS `shade()`/`alpha()`, and `qt-colors.conf` (which has no functions at all) falls back to one documented neutral grey for the disabled-state roles.

### GTK + Qt specifics

Theming flows through the standard mechanisms; **do not** re-introduce the old `env = GTK_THEME,...` override (it defeats the portal and only reaches Hyprland-spawned apps), nor `GSETTINGS_SCHEMA_DIR` (redundant, shadows app schemas), nor `GTK2_RC_FILES` (hyprland doesn't expand `~`, so it exported a dead literal path).

**GTK colours are overridden, not rebuilt.** Sweet-Custom declares 114 `@define-color` names, and a user `~/.config/gtk-{3,4}.0/gtk.css` is parsed *after* the theme — so the generated `gtk.css` redefines a subset and wins. Widget shapes and assets stay Sweet-Custom, there is no SCSS rebuild, and the committed-CSS drift hazard below is avoided entirely. Those two `gtk.css` files are **generated but tracked** (`!/gtk-3.0/gtk.css` negations in .gitignore): the `/gtk-3.0/*` rule would otherwise swallow them and a fresh clone would have no palette. The same reasoning makes every generated colour file tracked — `hypr/looknfeel.lua` does `require("theme/colors")`, so an untracked `colors.lua` means a *broken compositor config* on clone.

- **GTK 3/4**: `gsettings` keys under `org.gnome.desktop.interface` (theme `Sweet-Custom`, icons `Sweet-Purple`, cursor `Adwaita`/24, `color-scheme prefer-dark`) plus `~/.config/gtk-{3,4}.0/settings.ini` (both tracked; the rest of those directories, e.g. `bookmarks`, is machine-local and ignored). `xdg-desktop-portal` (portals.conf, `Settings` impl = hyprland, fallback gtk) exposes these to sandboxed and non-Hyprland-launched apps alike. Keep gsettings and both `settings.ini` files in sync — but note the two files are *not* interchangeable: `gtk-toolbar-style`, `gtk-toolbar-icon-size`, `gtk-button-images` and `gtk-menu-images` are GTK3-only and make GTK4 log `Unknown key ...` on every app start.
- **GTK 2**: `~/.gtkrc-2.0` (read by default; no env var needed).
- **Qt**: `hl.env("QT_QPA_PLATFORMTHEME", "qt6ct")` in `env.lua` → `qt6ct` applies the `Fusion` style + the **generated** `~/.config/qt6ct/colors/wallust.conf` palette (`custom_palette=true`). `kvantum`/`kvantum-qt5` are installed for SVG Qt theming if needed. `qt5ct` gets the same generated file so the two can no longer drift, though `/qt5ct/` itself stays gitignored.
- `hyprsysteminfo` (a QML app) is launched directly by `SUPER+I`; there is no theming wrapper script anymore.

The house palette is cyberpunk (`#161925` background, `#5de5ff` cyan, `#00b8e6` deep cyan, `#c7f5ff` light cyan, `#d946ef` magenta, `#b456f0` purple, `#c3c7d1` foreground). It is defined **once**, in [wallust/colorschemes/cyberpunk.json](wallust/colorschemes/cyberpunk.json) — edit it there and run `theme-switch cyberpunk`, never by hand-editing a consumer.

### Wallpaper

`awww` (a swww fork) replaced hyprpaper, so theme switches animate the wallpaper instead of swapping instantly. [wallust/set-wallpaper](wallust/set-wallpaper) starts `awww-daemon` if needed, waits for its socket, and sets a per-output image; it is called from `autostart.lua` and from `theme-switch`. Per-theme wallpapers are optional — drop `wallust/wallpapers/<theme>-<OUTPUT>.jpg` or `<theme>.jpg` and it picks them up, otherwise it uses the default Cyberpunk pair. `hypr/hyprpaper.conf` is kept, marked UNUSED, as a one-line revert path.

Two traps when touching this: get output names from `hyprctl -j monitors | jq -r '.[].name'`, **not** a `sed` on `"name"` — the monitors JSON also has nested `activeWorkspace.name`/`specialWorkspace.name`, so a naive match yields `("HDMI-A-1" "2" "" "DP-1" "1" "")`. And `awww img -o ""` means *every* output, so an empty name silently puts one wallpaper on all monitors (this exact bug shipped and was caught in testing).

## Shell (zsh + starship)

The login shell is **zsh**, configured via `ZDOTDIR`. A two-line untracked `~/.zshenv` stub sets `ZDOTDIR="$HOME/.config/zsh"` so the real config is tracked here at [zsh/.zshrc](zsh/.zshrc) — that stub must stay in `$HOME`, since zsh reads `~/.zshenv` before it knows about `ZDOTDIR`.

Everything is in `.zshrc` rather than `.zprofile` because terminals here spawn zsh as a **non-login** interactive shell (alacritty passes no `-l`), so `.zprofile` would never run. That also matches the old `.bashrc`, which returned early when non-interactive. `~/.bashrc` is kept working as a fallback.

- **`typeset -U path PATH fpath`** keeps PATH de-duplicated; the old `.bashrc` could stack entries.
- **CUDA 12.4 is pinned deliberately — do not "modernise" it.** Arch's `cuda` package is 13.3.1 at `/opt/cuda` and `/etc/profile.d/cuda.sh` already appends it, but `/usr/local/cuda` → `cuda-12.4` and the libtorch build in `/usr/local/libtorch` is built against 12.4. Prepending `/usr/local/cuda-12.4/bin` is what makes `nvcc` resolve to 12.4.131. (The `cuda-12.8` component of `PKG_CONFIG_PATH` *is* dead — that directory does not exist — but is harmless and kept verbatim.)
- **Secrets are never in a shell rc.** `~/.config/secrets/env` (chmod 600, gitignored via `/secrets/`) is sourced by both `.zshrc` and `.bashrc`. A plaintext `ghp_` GitHub token previously sat inline in `~/.bashrc`; it was moved here, and **should be revoked and reissued** — relocating it does not undo the exposure.
- `fastfetch` runs only when `SHLVL == 1` (a freshly opened terminal), not in every subshell; `nvidia-smi` no longer runs at startup at all and is the `gpu` alias.
- `starship.toml`, the `btop` theme and `fastfetch/config.jsonc` are all **generated by wallust**, so the terminal follows the desktop theme. `bat` is the exception — its themes are Sublime `.tmTheme` XML, so it uses a static `Dracula`.

## Editing conventions

- The compositor config is **Lua**. Check syntax before reloading — `luac -p hypr/*.lua hypr/theme/*.lua` catches typos instantly and costs nothing. The current wiki (`wiki.hypr.land`) documents Lua by default, which now matches this repo; the docs site is a JS-rendered SPA, so `curl`/WebFetch on a guessed path often 404s even when the page exists — find the real path from the rendered sidebar nav (`<a href=...>`) first. Prefer the local `/usr/share/hypr/stubs/hl.meta.lua` over the wiki for field names.
- Non-obvious hyprlang→Lua translations, in case anything is still unconverted: `exec-once` → `hl.on("hyprland.start", ...)`; `source` → `require`; `bezier = n,x1,y1,x2,y2` → `hl.curve(n, {type="bezier", points={{x1,y1},{x2,y2}}})`; `bindm`/`bindel`/`bindl` → options tables `{mouse=true}` / `{locked=true,repeating=true}` / `{locked=true}`; `killactive` → `hl.dsp.window.close()`; `movefocus,l` → `hl.dsp.focus({direction="left"})`; shadow `color = rgba(161925ee)` → the packed integer `0xee161925`. Lua `hl.window_rule` **requires** a `name` field, which has no hyprlang equivalent.
- Waybar config is JSONC (`.jsonc` — comments are allowed despite the `.json`-like content).
- Shell scripts under `waybar/` and `wallust/` are plain bash; they must stay idempotent/race-safe since they're invoked both from Waybar's polling and from a Hyprland keybind concurrently. The night-mode scripts achieve this by holding no local state at all — they read/write the running `hyprsunset` daemon over IPC, so there's nothing to race on. When a value comes from an external command, guard it before arithmetic (`[[ "$x" =~ ^[0-9]+$ ]]`); several scripts here previously threw "integer expression expected" when a query returned empty.
- Keep the `programs.lua` table indirection for anything that names an application binary, rather than hardcoding the binary name in multiple `hl.bind` lines.
- **Never hand-edit a generated file.** `waybar/colors.css`, `rofi/colors.rasi`, `swaync/colors.css`, `alacritty/colors.toml`, `gtk-{3,4}.0/gtk.css`, `qt*ct/colors/wallust.conf`, `superfile/theme/wallust.toml`, `hypr/theme/colors.{lua,conf}`, `starship.toml`, `fastfetch/config.jsonc`, `btop/themes/wallust.theme` and `rofi/icons/*.svg` are all overwritten on the next theme switch. Edit `wallust/templates/` or the colorscheme instead. Each generated file carries a "GENERATED" header saying so.
- **Watch out for escape sequences when writing files with tooling.** Writing `` into a config can land a *raw* ESC byte in the file, which broke both `alacritty.toml` (invalid control char in a TOML basic string) and `fastfetch/config.jsonc` (JSON forbids raw control characters). After writing any file containing escapes, verify with `grep -cP '[\x00-\x08\x0b-\x1f]' <file>` — it should be 0. Prefer an option that avoids escapes entirely (fastfetch's `outputColor` instead of an inline ANSI sequence).

## Applying changes (no build/test step — these are the closest equivalent)

- Hyprland: `hyprctl reload` re-reads `hyprland.lua` **and its `require`d modules** without restarting the session (verified). `hyprctl reload full-reset` rebuilds the whole config context and is what switches between Lua and hyprlang. Remember `hyprland.start` does not re-fire, so autostart changes need a real login.
- Waybar: `pkill -USR2 waybar` reloads config + stylesheet in place; a full `pkill -x waybar && setsid waybar &` is the fallback.
- Colours/themes: `wallust/theme-switch <name>` regenerates every consumer and reloads them. Never reload consumers by hand after a palette edit — use the switcher so nothing is missed.
- hypridle/hyprlock: restart the individual process. Wallpaper: `wallust/set-wallpaper`.
- zsh: open a new terminal, or `exec zsh`. Validate with `zsh -n ~/.config/zsh/.zshrc`. Note `zsh -i -c` **without a tty** emits spurious `can't change option: zle` errors — that is an artifact of having no terminal, not a config bug; test in a real PTY (`script -qec 'zsh -i -c ...' /dev/null`) before chasing it.
- systemd user units: `systemctl --user daemon-reload && systemctl --user restart <unit>` after editing files under `systemd/user/`.

There is no linter, formatter, or automated test suite in this repo; validate changes by reloading the affected program and, where feasible, visually/functionally checking the result (this repo also has access to the `run` skill's general guidance about exercising a change before declaring it done — apply that spirit here by reloading/restarting the relevant daemon).

## Diagnosing Hyprland config errors

Don't rely on `hyprctl reload`'s own output (`ok`) as proof the config is valid — it doesn't surface parse errors. Instead:

- `hyprctl configerrors` (or `hyprctl -j configerrors` for JSON) lists every current config error with file and line number. This is the fastest way to find deprecated/removed options and dispatchers after a Hyprland upgrade — check it first, before grepping the config by hand. `luac -p` first for pure Lua syntax errors, since a file that fails to parse never reaches Hyprland's option validation.
- **`configerrors` being empty does not prove the Lua config is the one live.** To confirm authority, set a distinctive value in Lua only and read it back — e.g. `border_size = 7` then `hyprctl -j getoption general:border_size`. A subtler tell: values coming from Lua are properly typed in `getoption` output (`"gradient"`, `"css"`, `"bool"`), whereas hyprlang reported everything as `"custom"`/`"int"`.
- Startup log lines about which config was chosen (`Using lua config found at ...` / `Lua config not found, using legacy config`) are written **once at compositor start** and are not re-emitted on reload, so a stale line there can mislead. The log is also flooded with DRM cursor noise — filter it.
- The live compositor log is at `/run/user/$UID/hypr/<instance-signature>/hyprland.log` (get the instance signature from `hyprctl instances` or by listing that directory). `grep -n "ERR \]" ` on it shows dispatcher/parse errors hit at startup (e.g. `Invalid dispatcher: togglesplit`), though `configerrors` is the more complete and current source of truth.
- To confirm a dispatcher name/args are valid without guessing from docs, test it live with `hyprctl dispatch <name> <args>` — but only for side-effect-free or easily-reversible dispatchers (e.g. `pseudo`, `layoutmsg togglesplit`). Never test `exit`, `killactive`, `exec`, or similar against the user's live session.
- To check whether a specific config option currently exists/what it's set to: `hyprctl -j getoption <category>:<name>` returns `"no such option"` if it's been removed.
- Cross-reference candidate replacement syntax against `strings $(which Hyprland) | grep -i <keyword>` — the binary's embedded option/dispatcher/error-message strings are a fast, version-exact way to confirm a name before trusting a docs page (which may describe a different Hyprland version, see above).
